# Missing Sender Validation in chrome.runtime.onMessage Handler

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-07-29 02:48:23 UTC
**Target:** /workspace/chat/App.tsx
**Endpoint:** App.tsx
**Method:** onMessage
**CWE:** CWE-862
**CVSS:** 6.5
**Fix Effort:** Trivial

## Description

The `handleMessage` callback registered via `chrome.runtime.onMessage.addListener` in App.tsx does not validate the message sender. The function signature accepts only `message: any` and ignores Chrome's `sender` parameter (`chrome.runtime.MessageSender`). This allows any other Chrome extension that knows this extension's ID to send spoofed `providerSettingsUpdated` messages, triggering page reloads, fake notifications, and potential model configuration manipulation.

## Evidence

The handler at App.tsx lines 99-123:

```typescript
useEffect(() => {
  const handleMessage = async (message: any) => {
    if (message.action === 'providerSettingsUpdated') {
      try {
        if (rootStore.robotStore.selectedRobot) {
          const chatModel = rootStore.llmStore.chatModel;
          await rootStore.robotStore.updateSelectedRobot({
            ...rootStore.robotStore.selectedRobot,
            model: chatModel,
          });
          window.location.reload(); // ← Destructive action
        }
        messageApi.info('提供商设置已更新');
      } catch (error) {
        console.error('更新提供商设置时出错:', error);
        messageApi.error('更新提供商设置失败');
      }
    }
  };

  chrome.runtime.onMessage.addListener(handleMessage);
  // Note: no sender.id check, no sender verification at all

  return () => {
    chrome.runtime.onMessage.removeListener(handleMessage);
  };
}, []);
```

## Impact

A malicious extension that discovers this extension's ID can:

1. **Denial of Service**: Repeatedly trigger `window.location.reload()`, making the extension page unusable
2. **Social Engineering**: Display fake error/info notifications to trick the user (e.g., fake error messages asking for credentials or inducing clicks)
3. **Model Manipulation**: Potentially influence which AI model is selected for chat, altering the data flow of the extension

## Technical Analysis

The `handleMessage` function is registered as a `chrome.runtime.onMessage` listener within a `useEffect` hook (lines ~99-123 of App.tsx). Chrome's runtime messaging API provides a `sender: chrome.runtime.MessageSender` object as the second argument to listeners, which includes `sender.id` — the extension ID of the sender. However, the handler's signature is:

```typescript
const handleMessage = async (message: any) => {
```

This omits both `sender` and `sendResponse`. Consequently, **no sender verification is performed** before processing the `providerSettingsUpdated` action.

In Chrome's extension messaging architecture, `chrome.runtime.onMessage` receives messages from:

- The extension's own components (background scripts, popups, options pages, content scripts)
- **Other extensions** that call `chrome.runtime.sendMessage(targetExtensionId, message)` with this extension's ID

Chrome extension IDs are deterministic (derived from the signing public key) but discoverable. Any Chrome extension or externally connectable webpage that knows this extension's ID can exploit this handler.

The handler performs several state-changing actions:

1. Updates the selected robot's model from `llmStore`
2. Calls `window.location.reload()` — reloads the extension's entire page
3. Shows `messageApi.info('提供商设置已更新')` or `messageApi.error('更新提供商设置失败')` — user-facing notifications

None of these actions are guarded by sender validation.

## Proof of Concept

1. Identify the target extension's ID (visible in chrome://extensions, Chrome Web Store URL, or via content script)
2. From any other extension's background script or popup, send: `chrome.runtime.sendMessage(targetExtensionId, {action: 'providerSettingsUpdated'})`
3. Observe that the target extension's page reloads and a notification "提供商设置已更新" is displayed
4. Repeat the message to trigger continuous page reloads, making the extension unusable

```javascript
// This code runs in any extension that knows the target extension ID
const TARGET_EXTENSION_ID = 'abcdefghijklmnopabcdefghijklmnop'; // Replace with actual ID

// Trigger page reload + fake notification (DoS)
chrome.runtime.sendMessage(TARGET_EXTENSION_ID, {

});

// Repeated calls for sustained denial of service
setInterval(() => {
  chrome.runtime.sendMessage(TARGET_EXTENSION_ID, {
    action: 'providerSettingsUpdated',
  });

```

## Remediation

Add sender validation as the first check inside the `handleMessage` callback:

1. Accept the `sender` parameter in the function signature: `(message: any, sender: chrome.runtime.MessageSender)`
2. Verify `sender.id === chrome.runtime.id` before processing any message
3. Optionally use `chrome.runtime.onMessageExternal` if external messages are intended, but for internal extension communication, always validate `sender.id`

## Assumptions

Assumes an attacker controls another Chrome extension installed in the same browser, or can inject code into a page that has access to `chrome.runtime.sendMessage` (via `externally_connectable`). The extension ID is discoverable through the Chrome Web Store URL, extension update manifests, content scripts, or chrome://extensions page.
